What OTIS does for the Sailor

Take over the watch.
Get to the tasking.

Catch up on traffic since turnover. Focus on the ships you’re watching. Check the next event, open the order behind it, and prepare an acknowledgement—all in the same watch desk.

  1. 01 / INCOMING TRAFFIC

    Bring the tasking into view.

    OTIS monitors a configured inbox and extracts activities, frequency plans, crypto changeovers, reporting requirements, locations, and contacts from supported OPTASK layouts.

  2. 02 / WATCH TURNOVER

    Catch up since the last watch.

    Review published messages issued since a selected UTC watch boundary. Filter by ship, see sent and received times separately, and open each message’s processing history.

  3. 03 / YOUR WATCH PICTURE

    Focus on the ships you’re watching.

    Select ships and compare their day schedules side by side, or browse a week or month. See timed activities and supported recurring changeovers in Zulu or your selected time zone.

  4. 04 / FIND A MESSAGE

    Search beyond the exact wording.

    One search combines keywords and meaning. Narrow message results by type, sender, and issue date, then open the message you need.

  5. 05 / CHECK THE ORDER

    Go back to what the message says.

    Open a schedule item’s source message. Switch between labeled USMTF fields, the original text, and the recorded intake and processing history.

  6. 06 / MESSAGE LOCATIONS

    See the locations on a map.

    When a message contains usable coordinates, view its points and supported shapes on a map. Pan and zoom using bundled map data.

  7. 07 / ACKNOWLEDGEMENT

    Prepare the response for review.

    Choose an acknowledgement type and generate a formatted AKNLDG draft using the source message and configured command details. Save it privately or copy it; the draft remains unsent.

  8. 08 / TRAFFIC STATUS

    Know when traffic needs attention.

    In-app notifications flag new messages, intake and publication failures, and recovery. Open the related message when available, and keep track of what you’ve read.

Built to run locally. OTIS retains accepted source emails, avoids duplicate message entries, and retries interrupted work. The application, search, and maps run locally without a GPU; disconnected use requires prepared runtime assets and the configured local services.

The order stays the reference. Coverage is based on tested OPTASK layouts. Check the original message when timing is incomplete, and confirm command applicability before acting. “Since last watch” lists traffic by issue time; it does not identify amendments or cancellations.

Supporting detail

What supports this briefing.

Briefing refined 05 Nov 2026. Prior validation is attributed to the project records below; application test suites were not rerun for this presentation. No source traffic is embedded.

  • Capabilities checked against the current interfaceREADME.md · apps/watch-desk/ui/src/pages/calendar.tsx · apps/watch-desk/ui/src/components/

    The current interface includes ship-filtered schedules, watch turnover, combined keyword and semantic search, parsed/raw messages, lifecycle history, coordinate-based maps, private acknowledgement drafts, and notifications. The reader does not expose a detailed extraction-audit view; the calendar does not display a separate unresolved-time review list.

  • Use case, required outcome and optional features.pdlc-docs/command-tasking-visibility/

    Formatted message input; command-relevant tasking; frequency, crypto and flight-quarter timing; 24-hour visual schedule; coordinating POC. Draft responses and conflict awareness are nice-to-haves.

  • Fourteen tested OPTASK profiles / approved example factsREADME.md → Supported OPTASK messages · backend/README.md

    13 periods, 27 frequencies, 25 activities and 8 contacts. Example/profile-specific regression coverage; not full USMTF edition compliance or a measured operational accuracy score.

  • Integrated application and end-to-end verificationdocs/integration/rust-integration-validation.md

    Documented local React → Rust → OpenSearch workflow, email-to-search synthetic test, preserved private state, duplicate handling and restart behavior. Records 47 passing UI tests; compatible canonical Ark orchestration was unavailable.

  • Source traceability, time semantics and private preparationdocs/integration/rust-application-api.md

    The service retains extraction audit records and provides an evidence API; that detailed view is not connected to the current message reader. The reader exposes parsed source fields, raw text, and lifecycle history. Private unsent drafts remain tied to the message revision.

  • Local search and disconnected executiondocs/integration/rust-integration-validation.md · backend/search/README.md

    CPU-based local embeddings and combined keyword/semantic retrieval. Prior cold deployment/inference/retrieval checks ran with OpenSearch disconnected from its application network. Prepared assets and enforced enclave isolation are required.

  • Readiness and benefit boundariesbackend/INTAKE.md · deploy/uds/VALIDATION.md · docs/integration/rust-integration-validation.md

    Verified IMAP TLS, token validation and ARM64 UDS packaging have been added. Target-platform mailbox and identity acceptance, retention, full disconnected recovery and large-burst capacity still need validation. Command/C2 resolution and flight-quarters coverage need domain validation. Time saved, error reduction and fleet-wide scalability are not measured outcomes.

  • Judging weights

    Supplied screenshot: Warfighting & Deckplate Impact 30%; Speed to Fleet 20%; Fleet Scalability 20%; Barrier Removal 15%; Judges’ Discretion 15%. The briefing claims no self-assigned scores.
